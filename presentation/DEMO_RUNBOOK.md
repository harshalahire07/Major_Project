**Project**: An Evidence-Grounded AI System for Document Question Answering, Hallucination Detection, and Claim-Level Repair  
**Target Environment**: Local Windows Workstation (RTX 2050 4GB VRAM, AMD Ryzen 5, 16GB RAM)  
**Academic Milestone**: Final Major Project Examination (B.Tech CSE 2026–27)

## 1. Demonstration Philosophy & Scope

### Implemented vs. UI Scaffold Status
- **Backend Service Layer**: 100% fully implemented and operational. Supports PDF upload, PyMuPDF page-tracking extraction, BGE-small chunk embeddings, FAISS scoped retrieval, Qwen3-4B draft generation, atomic claim decomposition, DeBERTa-v3 cross-encoder NLI verification, targeted LLM claim repair, mandatory re-verification, and final answer reconstruction with page citations.
- **REST API & Swagger UI**: Fully interactive at `http://localhost:8000/docs`. Every internal pipeline state (original draft, atomic claims, verification scores, repair history, re-verification states, citations) is queryable and inspectable.
- **Frontend UI**: Currently a client scaffold (`App.tsx`). For final examination demonstration, the primary evaluation and pipeline inspection should be conducted via the **FastAPI Swagger UI** and authenticated curl/HTTP scripts, with the frontend dev server running to demonstrate cross-origin connectivity.

## 4. Live Demonstration Workflow (Swagger UI & REST API)

Open your browser to the interactive Swagger UI:  
**`http://localhost:8000/docs`**

### Demonstration Step 1: Inspect Ingested Documents
Expand `GET /api/v1/documents` and click **Execute**.
- **Observation**: Shows the list of indexed research documents (e.g., `Provenance`, `FactLens`, `SciHal`, `HalluCorrect`) with their page counts and document UUIDs.
- **Key Talking Point**: Highlight that physical page counts are stored in PostgreSQL while dense chunk embeddings reside in FAISS.

*(Optional Ingestion Demo)*: If uploading a new PDF:
- Expand `POST /api/v1/documents`.
- Select a sample PDF from `docs/`.
- Execute and show the returned `document_id`, filename, and chunking progress.

---

### Demonstration Step 2: Execute Baseline RAG (`mode="baseline"`)
Demonstrate traditional RAG to establish the experimental control.

Expand `POST /api/v1/queries` and submit the following JSON payload:
```json
{
  "question": "What is the main goal of the SciHal paper?",
  "document_ids": ["adfce3b1-651c-4519-8992-5396032b2150"],
  "mode": "baseline"
}
```
- **Execution Time**: ~12 – 15 seconds.
- **Response Inspection**:
  - `draft_answer`: Fluent answer generated by Qwen3-4B.
  - `final_answer`: Exact copy of draft answer.
  - `claims`: `[]` (Empty list — baseline bypasses verification).
  - `latency_seconds`: ~14 seconds.
- **Talking Point**: Note that while the answer is fluent, there is **zero verification**, no attribution, and no protection if the model extrapolated or hallucinated numbers.

---

### Demonstration Step 3: Execute Proposed Full Verification Pipeline (`mode="full"`)
Demonstrate the core contribution of the Major Project.

Submit the exact same query with `mode="full"`:
```json
{
  "question": "What is the main goal of the SciHal paper?",
  "document_ids": ["adfce3b1-651c-4519-8992-5396032b2150"],
  "mode": "full"
}
```
- **Execution Time**: ~55 – 75 seconds (explain the multi-stage latency overhead during inference).
- **Inspect Response Structure**:
  1. **`draft_answer`**: Initial raw generation before verification.
  2. **`claims` list**: Show atomic claim decomposition:
     - `original_claim_text`: Discrete propositions isolated by the decomposer.
     - `original_verification_result`: Status (`SUPPORTED`, `CONTRADICTED`, `UNVERIFIABLE`) and cross-encoder probabilities (`entailment_score`, `contradiction_score`).
     - `evidence`: Shows retrieved chunk text with exact page numbers (e.g., `page_number: 1`).
  3. **Targeted Repair Inspection** (if a claim was contradicted):
     - `current_claim_text`: Shows rewritten claim.
     - `repair_history`: Audit record showing the prompt, repair attempt, and re-verification score.
     - `repair_status`: `REPAIRED` or `FLAGGED`.
  4. **`final_answer`**: Reconstructed deterministically from verified claims with page citations:
     - Example: *"[Claim text] (Page 1)"*.

---

### Demonstration Step 4: Demonstrate Adversarial / Contradiction Query
To show hallucination detection and repair in action, submit a query containing an incorrect or adversarial premise:
```json
{
  "question": "Did SciHal use a completely unsupervised approach without any fine-tuning?",
  "document_ids": ["adfce3b1-651c-4519-8992-5396032b2150"],
  "mode": "full"
}
```
- **Expected Pipeline Behavior**:
  - Initial draft attempts to answer or falsely adopts the premise.
  - Decomposed claim is flagged as **`CONTRADICTED`** against the retrieved premise (*"fine-tuning DeBERTa-v3"*).
  - Targeted repair rewrites the statement to align with the text.
  - Re-verification checks the repaired assertion.
  - Final answer excludes unverified assertions.

## 5. Failure Modes & Live Demo Mitigations

| Potential Live Issue | Root Cause | Immediate Mitigation / Backup Plan |
| :--- | :--- | :--- |
| **Query Hangs / Timeout (>120s)** | GPU memory contention or thermal throttling on 4GB VRAM. | Kill running query task. Demonstrate using the pre-evaluated artifacts in `evaluation/results/full.jsonl` or re-run a simpler factoid query (`q001` or `q003`). |
| **Model returns `UNVERIFIABLE`** | Evidence chunk missed in Top-3 retrieval. | Explain Slide 10: *UNVERIFIABLE does not mean false*. Show that evidence expansion was triggered. |
| **Ollama connection refused** | Ollama background process exited. | Launch PowerShell: `ollama serve`. Re-test with `curl http://localhost:11434/api/tags`. |
| **PostgreSQL connection refused** | PostgreSQL service stopped. | Run `Start-Service postgresql*` or `docker compose start`. |

## 6. Demonstration Talking Script (2-Minute Pitch)

> *"Honorable committee members, what you are seeing here in our live API demonstration is the fundamental difference between standard generative RAG and our Evidence-Grounded Verification Architecture.*
> 
> *In Mode A (Baseline), the system generated a plausible paragraph in 14 seconds. However, that paragraph was a black box—we had no way to know if sub-task scores or model names were hallucinations or genuine facts.*
> 
> *In Mode B (Full Pipeline), our orchestrator treated that generation merely as an untrusted draft. It extracted 5 atomic propositions, retrieved localized chunk evidence for each one, and ran them through an independent DeBERTa-v3 cross-encoder. Claims that were supported were preserved with exact page citations. When a claim was contradicted by source text, our targeted repair service isolated that single claim, rewrote it against the evidence chunk, and re-verified it before assembly.*
> 
> *While this multi-stage auditing introduces latency overhead—which our pilot benchmarks measure at approximately 51.5 seconds—it converts generative AI from an untrusted black-box into an auditable, evidence-backed information system."*
